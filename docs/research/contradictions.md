# Contradictions between research reports

Raised by the two completeness critics. The architecture resolves each one in [../04-architecture.md](../04-architecture.md) and the ADRs.

## First pass

1. Fog-of-war refresh. Engine §4.4 (and Platforms §5.2 point 2) say a unit whose visibility flips inside one section is not re-checked unless the mod forces it. Libraries §3.8, Mechanics §1.18 and Prior-art §10 say the movement packet sent at least every 20 ticks re-checks it within ~1 s with no hook. Source check: that packet is sent only while the player is its own camera (LocalPlayer.java:277/700); nothing is sent under a client-side camera entity, while ServerPlayer#setCamera re-checks every tick (ServerPlayer.java:527). Which is true depends on the camera design (gap 2).
2. Content definitions. Libraries §3.3/§3.9 and Platforms §6.4(8) put units, buildings, techs and civs in datapack registries. Engine §6 and Mechanics §2.11 put templates in a reload listener with custom inheritance and keep registries for stable IDs only (gap 6).
3. Authoritative unit state. Engine §3.2/§7 makes SavedData records authoritative, treats entities as views and rules out chunk attachments for map-wide data. Libraries §3.9 stores per-unit state (owner, order queue) in entity attachments and territory and exploration in per-chunk attachments (gap 1).
4. Stats. Prior-art §3.4/§12 recommends unit stats as registered, syncable vanilla Attributes. Mechanics §2.3 and Platforms §6.4(1) compute stats through a Minecraft-free modifier pipeline in core (gap 1).
5. Determinism versus movement and pathing. Testing §4 and Mechanics §2.7 expect seeded whole-match replays in core JUnit. But Engine §1.4 keeps vanilla travel/move physics on the entity, and the RoN-style worker pool that delivers results when ready (Libraries §3.10, Engine §2.3) is not deterministic unless results land at a fixed tick, as 0 A.D.'s turn-start delivery does (gap 1).
6. jqwik. Libraries §3.12/§5 pins jqwik 1.10.2 and Platforms §7.2 lists jqwik as optional. Testing §0/§4 bans jqwik ≥ 1.10. The jqwik release notes saved under research-testing confirm the Testing report: 'Starting with version 1.10 jqwik comes with an Anti-AI Usage Clause! Usage with any AI agent is strongly discouraged.'
7. EphemeralTestServerProvider. Platforms §6.4(9)/§7.4 prefers JUnit with it for live-server integration tests. Testing §5 restricts it to datapack and codec checks, and so does the class's own Javadoc ('should NOT interact with the world … use a GameTest'). The testframework source confirms that initServer() never loads a level.
8. GameTest wiring. Platforms §7.2–7.3 makes GameTests a separate test mod 'strategos_gametest' with its own mods.toml and namespace. Testing §3.2/§6.2 adds gametest and devtools source sets to the 'strategos' mod itself and filters on 'strategos'. Neither setup has been run.
9. Force-loading the match area. Mechanics §1.25/§2.11 uses TicketController.forceChunk(..., ticking=true). Engine §3.1 says ticking=false already makes each forced chunk entity-ticking, and ticking=true adds random ticks and natural mob spawning. Confirmed in ServerChunkCache#tickChunks: shouldForceTicks calls NaturalSpawner.spawnForChunk when doMobSpawning is on.
10. Server budget. Testing §9 caps the mod's own server work at ≤5 ms p50 and ≤10 ms p99 for 4 × 200 units. Engine §1.2 gives units ~20 ms of the 50 ms tick (600–800 vanilla-AI or 1,500–2,000 stripped units). Neither figure is measured, and they differ by a factor of 4.
11. Pathfinding. Mechanics §2.8 proposes JPS/A* over a 2.5D per-column grid with chunk regions. Engine §2.2 says JPS's uniform-cost assumption breaks under step, drop, water and door costs, and uses per-chunk cell classes over a Y band instead. Prior-art §9 notes that RoN uses a 3D grid and that FrostedHeart's 2.5D field fails on caves and overhangs.
12. RTS input capture. Libraries §3.2 says interactive RTS mode needs a non-pausing Screen that owns the cursor. Engine §5.1 and Prior-art §7 (Camera Lib) release the mouse and cancel InputEvent.MouseButton.Pre with no screen open. The two approaches handle keybinds, chat and HUD layers differently.
13. Acceptance tests. Mechanics §4.1 asks for a GameTest of a 200-unit cross-map move. Testing §6.4 limits structure arenas to 48 blocks per axis (larger sizes are unverified) and runs all tests in a batch concurrently in one world.
14. GPL route. Prior-art §11 treats GPL-3.0 code (RoN, MineColonies) as reusable if Strategos itself goes GPL-3.0. Mechanics §3 cites the FSF view that a GPL plug-in forming one program with a nonfree host (Minecraft) violates the GPL unless an exception is granted, which weakens that route.
15. Loader and toolchain. All six reports agree on NeoForge 21.1.264, MDG 2.0.148 and a Java 21 toolchain. The only pin conflict is junit-bom 5.14.1 (Platforms §7.3) against 5.14.4 (Libraries §5, Testing §1).

## Second pass

1. Content definitions. Platform §6.4.8 and Libraries §3.3 put units, buildings, techs and civs in datapack registries. Engine §6 and Mechanics §2.1/§2.11 put them in a reload listener with 0 A.D.-style parent/mixin inheritance and keep registries for stable ids only (gap 5).
2. Keeping the match area alive. Mechanics §1.25/§2.11 force-loads the whole arena with TicketController.forceChunk(..., ticking=true). Engine §3.2 keeps authoritative records in SavedData, creates entities only in loaded chunks and caps follow-tickets (gap 4). Mechanics also has the flag wrong for its purpose. DistanceManager#addRegionTicket feeds the ticking tracker for both values, so entities tick in a forced chunk even with ticking=false. ticking=true (forceTicks) only adds random ticks and natural mob spawning where no player is near (ServerChunkCache#tickChunks), which would spawn vanilla mobs across an unwatched arena. Prior art §10 and Engine §3.1 state this correctly (verified in the decompiled 1.21.1 tree).
3. Per-chunk state. Libraries §3.9 keeps territory and exploration in chunk attachments. Engine §7 warns that chunk attachments exist only while the chunk is loaded, so they must not hold map-wide data for the minimap or AI. The two agree only if the whole arena stays loaded (gap 4).
4. Who owns unit state. Platform §6.4.1, Mechanics §2.7 and Testing §4 promise a deterministic core that does not touch Minecraft, with replay hashes. Engine §1.4 lets vanilla travel/move own position and keeps hot state in entity fields and SynchedEntityData. Libraries §3.9 keeps orders and owner in entity attachments. Engine §3.2 makes SavedData records authoritative. No report states the split (gap 1).
5. Budgets and scale. Testing §9 allows ≤5 ms p50 / ≤10 ms p99 of all mod server work and ≤3 ms per frame of mod rendering plus HUD, for 4 × 200 units and 100 buildings. Engine §1.2 plans about 20 ms per tick for units at 10–30 µs each, i.e. 8–24 ms for 800. Unit targets range from 150 per player (RoN) and 300 per player (0 A.D.) to 600–2,000 in total (Engine). Every per-unit figure is unverified (gap 1).
6. Pathfinding foundation. Mechanics §2.8 recommends a 2.5D column grid with off-thread JPS/A*. Engine §2.2 recommends Y-band cell classes and rejects JPS because of step, drop, water and door costs. RoN uses 3D A* in a ±24 band (gap 6).
7. Determinism vs async pathfinding. The promised deterministic core conflicts with the recommended best-effort worker pool (RoN, Engine §2.3): results are applied when ready, at most 256 per tick, and a 'busy' answer keeps the old path. 0 A.D. instead delivers results at a fixed turn boundary (Mechanics §2.6) (gap 6).
8. Cursor and camera. Libraries §3.2 says RTS mode needs a non-pausing Screen that owns the cursor. Engine §5.1 and its implication 7 free the cursor with releaseMouse plus a cancelled InputEvent.MouseButton.Pre. Camera Lib releases the mouse every tick, and RoN opens a container screen. Engine prefers moving the commander's player with the camera. Libraries §3.7 cites Freecam's camera entity as the Iris-safe reference, and Camera Lib and RTS Building also use camera entities (gap 2).
9. Fog-of-war re-check cadence. Engine §4.4 says a stationary commander never triggers re-evaluation. Libraries §3.8, Prior art §10 and Mechanics §1.18 say ChunkMap#move runs on every movement packet and the client sends one at least every 20 ticks. LocalPlayer#sendPosition confirms the 20-tick reminder, but only while isControlledCamera() is true, so which report is right depends on the camera design. Platform §5.2 and Mechanics §1.18 send every re-check through an access transformer on ChunkMap.entityMap. For a re-check per player, the public ServerChunkCache#move(ServerPlayer) (line 464) already does this; an AT is needed only to re-check one entity against all players.
10. JUnit integration tests. Platform §6.4.9 advises preferring JUnit with EphemeralTestServerProvider for integration tests. The Javadoc of testframework 21.1.264 (verified) says that server has only a void overworld and must not be used for world interaction; use GameTests instead, as Testing §5 also says.
11. GameTest wiring. Platform §7.3 uses a separate strategos_gametest mod with @GameTestHolder. Testing §6.2 keeps the GameTests in the strategos mod group and registers them through RegisterGameTestsEvent with its own generator, partly because vanilla swaps attempts and requiredSuccesses (verified: GameTestRegistry passes requiredSuccesses() into TestFunction.maxAttempts).
12. jqwik. Libraries §3.12/§5 add jqwik 1.10.2, and Platform §7.2 lists jqwik as optional. Testing §0/§4 forbids jqwik ≥ 1.10, because every run prints an instruction aimed at AI agents, and 1.10.0 told agents to delete tests. Testing's finding rests on primary sources (release notes, LWN) and should win: pin 1.9.3 or use seeded parameterized tests.
13. Building HP. Mechanics §1.6 keeps HP abstract and swaps in damaged-block palettes, because 'real block destruction would break pathing and invite griefing'. Prior art §12 adopts RoN's model: health = blocks placed, and the building is destroyed below 50%. Engine §8 offers both. The choice decides T0 construction, protection hooks and how often the nav grid is rebuilt.
14. GPL as an escape hatch. Mechanics §3, citing the FSF FAQ, argues that a GPL plug-in combined with the proprietary Minecraft host is itself problematic, so relicensing Strategos as GPL would not make copying 0 A.D. code clean. Engine §2.4 and Prior art §11 say copying GPL code 'only' forces Strategos to GPL-3.0. This matters little while all work is clean-room.
